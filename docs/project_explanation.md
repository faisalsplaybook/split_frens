# Split Frens — Project Explanation

## What I Built

Split Frens is a Flutter expense-splitting app designed for friend groups, hangouts, and trips. Users can create hangouts (group events), add participants, log shared expenses, and the app automatically calculates who owes whom using a greedy settlement algorithm. Settlements can be toggled as paid/unpaid, and formatted summaries can be shared via any messaging app.

The app also includes a currency converter feature for travel mode — users can log expenses in foreign currencies, and the app converts them to their base currency via the ExchangeRate-API.

## Why I Built It

I built Split Frens to demonstrate practical Flutter development skills through a real-world problem: splitting bills with friends. The project covers the full range of skills expected in a junior Flutter developer role:

- Complex state management with Riverpod
- Persistent local storage with Hive
- REST API integration with Dio
- Proper navigation with go_router
- Manual data models with JSON serialization
- Feature-first architecture with separation of concerns
- Unit testing with flutter_test

It's not a toy app — it solves a genuine problem that people face regularly when dining out, traveling, or sharing group expenses.

## Data Models

The app uses four core data models, all linked by IDs (a normalized architecture):

### HangoutModel
Represents a group event (e.g., "Weekend trip to Cox's Bazar"). Contains:
- `id`, `title`, `startDate`, `endDate`
- `participantIds` — list of person IDs in this hangout
- `expenseIds` — list of expense IDs logged to this hangout
- `paidSettlementIds` — tracks which generated settlements have been marked as paid

### ExpenseModel
Represents a single bill/expense (e.g., "Dinner — $90"). Contains:
- `id`, `title`, `amount`, `date`, `paidById`
- `splitType` — currently only `SplitType.equal`
- `participantIds` — who the expense is split among
- `currency`, `convertedAmount` — for travel mode currency conversion

### PersonModel
A simple name + ID model for participants. Contains:
- `id`, `name`

### SettlementModel
A calculated transaction generated by the split algorithm. Contains:
- `id` (deterministic, based on debtor + creditor + amount)
- `payerId` (who owes), `payeeId` (who is owed), `amount`
- `isPaid` — derived from `HangoutModel.paidSettlementIds`

## State Management

The app uses **Riverpod** (`NotifierProvider`) for all state management. Three core providers manage the normalized data:

- `hangoutsProvider` → `HangoutsNotifier` (manages `List<HangoutModel>`)
- `personsProvider` → `PersonsNotifier` (manages `List<PersonModel>`)
- `expensesProvider` → `ExpensesNotifier` (manages `List<ExpenseModel>`)

Each notifier loads initial data from Hive on startup (`build()`) and persists state to Hive after every mutation via a `_save()` helper. All three lists are saved together to maintain referential integrity between IDs.

There is also a `currencyProvider` for managing the async state of currency conversion API calls (loading, success, error states).

## Local Storage

All data is persisted locally using **Hive** (via `hive_flutter`). A single `LocalStorageService` class:

1. Opens a Hive box (`split_frens_box`) during app startup in `main()`
2. Stores all three data lists (hangouts, persons, expenses) as JSON strings under separate keys
3. Loads data on app restart by deserializing JSON back into model objects
4. Provides a `clearAllData()` method for full data wipe

Settings (like default currency) use **SharedPreferences** via a separate `SettingsStorageService`.

## API Integration

The currency converter uses the **ExchangeRate-API** free tier (`https://open.er-api.com/v6/latest/{currency}`). The integration follows a clean architecture:

1. **CurrencyApiService** — Makes the Dio GET request, parses the JSON response, extracts the exchange rate
2. **CurrencyRepository** — Wraps the API service, calculates `convertedAmount = amount * rate`
3. **CurrencyProvider** — Manages the async state (idle → loading → success/error) using a `CurrencyState` class

Error handling covers: network failures, unsupported currencies, malformed API responses. The UI shows loading spinners during API calls and error messages with retry buttons on failure.

## Calculation Logic

The `SplitCalculatorService` is the mathematical engine of the app. It performs four key calculations:

### 1. Total Spent
Sums all expense amounts in a hangout (using `convertedAmount` if available for travel mode).

### 2. Paid Amounts
Maps each participant to how much they actually paid out of pocket across all expenses.

### 3. Share Amounts
Maps each participant to how much they *should* have paid (equal split per expense based on participant count).

### 4. Net Balances
`Net = Paid - Share` for each person. Positive means they are owed money; negative means they owe.

### 5. Settlement Generation
Uses a **greedy algorithm** to generate the minimum number of transactions:
- Separate participants into debtors (negative balance) and creditors (positive balance)
- Repeatedly match the highest debtor with the highest creditor
- Create a settlement for the smaller of the two amounts
- Reduce both balances accordingly
- Repeat until all balances are settled

Settlement IDs are **deterministic** (`hangoutId_debtorId_creditorId_amount`) so that if the underlying expenses change, the settlement IDs change too, automatically resetting the paid status.

## Edge Cases

The app handles the following edge cases:

- **Empty states**: "No hangouts", "No people", "No expenses", "No settlements required" all display custom placeholder cards with clear CTAs
- **Missing hangout**: If a hangout ID doesn't exist in state (e.g., deep link to deleted hangout), screens show an error UI instead of crashing
- **Less than 2 people**: The "Add Expense" screen blocks entry and directs users to add friends first
- **Share with no expenses**: The Share button validates that expenses exist before generating a summary
- **Currency API failure**: Displays error text with a retry button; doesn't block the rest of the form
- **Rounding precision**: Uses `closeTo(0.01)` thresholds to handle floating-point arithmetic
- **Deterministic settlement IDs**: If expenses change, settlement IDs change, automatically resetting paid status
